# Interview notes

Short answers in English and Japanese. Updated as each milestone lands, and backed by numbers in `results.md`.

## Why atomic UPDATE over FOR UPDATE (or the reverse)? What did the numbers show?
- EN: Both are correct; naive read-then-write is not (it oversold by 1,142–1,499 units at 10,000 buyers vs 100). Atomic and FOR UPDATE both sold exactly 100 in every run. The difference is how long the single hot row stays locked. Atomic takes the lock in the UPDATE and holds it for UPDATE → COMMIT. Pessimistic takes it one round trip earlier, in the SELECT. In the write-path ceiling test, same session, atomic sustained 750 req/s twice; pessimistic managed 500 and then 250. I'd still pick FOR UPDATE when the decision can't be written as a WHERE clause (several rows, business rules in code). Also: plain `FOR UPDATE` deadlocked in my first version, because the reservation INSERT's foreign key takes KEY SHARE on the same row. `FOR NO KEY UPDATE` is the correct lock for updating a non-key column.
- JA: どちらも正しく、素朴な read-then-write は誤り（1万人×100個で1,142〜1,499個の売り越し）。atomicとFOR UPDATEはどの試行でも正確に100個。差はホット行のロック保持時間。atomicはUPDATEでロックを取り、UPDATE→COMMITの間だけ保持する。pessimisticは1往復早いSELECTで取る。同一セッションの書き込み上限試験では、atomicが2回とも750 req/s、pessimisticは500と250 req/s。それでも、判断がWHERE句で書けない場合（複数行やコード上の業務ルール）はFOR UPDATEを選ぶ。補足：最初の実装の `FOR UPDATE` はデッドロックした。予約INSERTの外部キーが同じ行にKEY SHAREを取るため。キー以外の列を更新するなら `FOR NO KEY UPDATE` が正しいロック。

## What happens on the hot row at 100× traffic, and what would you change?
- EN (draft, from L1/L5 data): Two different paths matter. Sold-out traffic only needs a lock-free read, and handled 4,422–7,489 req/s on a laptop. Writes to the single stock row are serialized: our full reserve path tops out at about 500 req/s (L5). Postgres alone did about 4,900 single-row updates/s in the same VM (pgbench), so the gap is round trips made while the row lock is held. In a 100-unit drop only about 100 requests ever write, so 100× buyers mostly stresses the read path and the connection pool. Changes, in order: (1) answer sold-out from a cached flag before taking a DB connection; (2) shorten the lock hold, with one-statement reserve (INSERT + UPDATE in a single CTE) and no network round trip between UPDATE and COMMIT; (3) if writes themselves become the limit (big drops), split stock into N bucket rows and take from a random one; (4) admission queue / waiting room so buyers enter at the rate the stock row can absorb.
- JA（暫定・L1/L5の計測より）: 経路が2つある。売り切れ応答はロック不要の読み取りだけで、ノートPCでも4,422〜7,489 req/s。在庫行への書き込みは直列化され、予約処理全体で約500 req/sが上限（L5）。同じVM内のPostgres単体では1行UPDATEが約4,900回/秒（pgbench）なので、差は行ロック保持中のラウンドトリップ。100個のドロップで書き込むのは約100リクエストだけなので、100倍の購入者が圧迫するのは主に読み取り経路と接続プール。対策の順序：(1) 売り切れはDB接続を取る前にキャッシュしたフラグで返す、(2) ロック保持時間の短縮（INSERTとUPDATEを1つのCTEで1往復に、UPDATEとCOMMITの間に往復を挟まない）、(3) 書き込み自体が上限になる大規模ドロップでは在庫をN行のバケットに分割し、ランダムな行から取る、(4) 在庫行が捌ける速度で入場させる待合室／アドミッションキュー。

## How does idempotency behave when two identical requests arrive at the same millisecond?
- EN: The key is inserted *inside* the same transaction as the reservation, with `ON CONFLICT DO NOTHING`. The second request's insert hits the uncommitted row from the first and Postgres makes it wait on the primary key. When the first commits, the second's insert affects 0 rows, so it reads and replays the stored response, byte for byte. If the first rolls back, the second's insert succeeds and it does the work itself. No polling and no lease, and the key and the effect commit atomically. Test: 50 identical requests at the same instant → 1 reservation, 50 identical responses, 49 marked replayed. Under load: about 14,000 requests per run with 983 double-clicks and about 3,000 same-key retries, 0 keys with two different effects. Only successes are stored: a sold-out has no effect, and storing it would add a write to the path that carries 99% of the traffic.
- JA: 冪等キーは予約と**同じトランザクション内**で `ON CONFLICT DO NOTHING` 付きでINSERTする。2件目は1件目の未コミット行に当たり、Postgresが主キー上で待たせる。1件目がコミットすれば2件目のINSERTは0行となり、保存済みレスポンスをバイト単位で同一のまま返す。1件目がロールバックすれば2件目が自分で処理する。ポーリングもリースも不要で、キーと効果が原子的にコミットされる。テスト：同一リクエスト50件を同時送信 → 予約1件、レスポンス50件すべて同一、うち49件が再送。負荷試験：1回約14,000リクエスト（二重クリック983件、同一キー再送約3,000件）で、2つの異なる効果を生んだキーは0件。保存するのは成功のみ。売り切れは副作用がなく、保存するとトラフィックの99％が通る経路に書き込みが増えるため。

## Why can't the race detector prove there is no oversell?
- EN: `-race` instruments memory accesses inside one Go process. Oversell is two *database transactions* interleaving (a lost update on `drops.remaining`). The Go side may have no shared memory at all, since each request has its own goroutine and its own connection. So the detector has nothing to flag. DB correctness is proven by constraints, the invariant checker, and load results.
- JA: `-race` は単一プロセス内のメモリアクセス競合のみ検出する。売り越しは DB トランザクション同士の lost update であり、Go 側に共有メモリが存在しないため検出対象外。DB の正しさは制約・不変条件チェッカー・負荷試験結果で証明する。

## What would break first if you deployed this as-is?
- EN (draft, milestone 3): The connection pool, not correctness. In the 10,000-buyer test with a 20-connection pool, the atomic strategy never oversold, but p95 reached 1.3–2.5 s because every request queues for one of 20 connections. With the naive strategy, 1,600–3,792 requests per run hit the 5 s deadline and got 503. The fix order: shed sold-out traffic before it needs a DB connection (a cached "sold out" flag), size the pool against measured numbers (milestone 5), then admission control in front of the hot row. _Expiry, payments, and idempotency gaps to be added after milestone 4–5._
- JA（暫定・M3時点）: 先に壊れるのは正しさではなくコネクションプール。10,000人・プール20の試験で、atomic戦略は売り越しゼロだったが、全リクエストが20本の接続を奪い合うためp95は1.3〜2.5秒。naive戦略では1回あたり1,600〜3,792件が5秒のタイムアウトで503に。対策の順序：売り切れ後のトラフィックをDB接続前に返す（売り切れフラグのキャッシュ）、計測に基づくプールサイズ調整（M5）、ホット行の前段にアドミッション制御。_期限切れ・決済・冪等性の論点はM4〜5後に追記。_

## Bonus: a concurrency bug you found and how
- EN: Confirm read the reservation and its payment in one `SELECT ... JOIN ... FOR UPDATE OF r`. Running the 20-concurrent-confirms test five times failed three times: some callers got "not held" instead of "payment failed". Under READ COMMITTED, a statement that waited for a row lock re-reads only the locked row at its newest version, while the joined table's row still comes from the snapshot taken before the wait. So a waiter saw a fresh `cancelled` reservation next to a stale `pending` payment. Fix: lock first, then read the payment in a separate statement. 15/15 afterwards. Lesson: concurrency tests must be repeated (`-count`), and stock was still safe because each state transition had its own `WHERE status=...` guard.
- JA: Confirmで予約と決済を1つの `SELECT ... JOIN ... FOR UPDATE OF r` で読んでいた。同時20件のconfirmテストを5回実行すると3回失敗し、一部が「payment failed」ではなく「not held」を返した。READ COMMITTEDでは、行ロックを待った文はロック対象の行だけを最新版で読み直し、JOIN先の行は待つ前のスナップショットのまま。そのため最新の `cancelled` と古い `pending` が組み合わさった。修正は、先にロックし、決済は別の文で読むこと。以後15回中15回成功。教訓：並行性テストは `-count` で繰り返すこと。各状態遷移に `WHERE status=...` のガードがあったため、在庫は修正前も安全だった。
